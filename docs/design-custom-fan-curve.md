# 自定义温控曲线 — 设计文档

> 状态：**设计已收敛，待实现**。
> 本文只描述设计，不含代码改动。所有标「建议值」的数字需实机标定后确认。

---

## 1. 背景与目标

### 现状

智能温控曲线在 `FanManager` 里**硬编码**，用户看不到也改不了（`fan/FanManager.kt`）：

| 温度 | 30 | 35 | 40 | 45 | 50 | 55 | 60 | 90 |
|---|---|---|---|---|---|---|---|---|
| 占空比 | 0% | 30% | 70% | 80% | 90% | 99% | 99% | 99% |

两个问题：

1. **默认曲线非常激进。** 40°C 就 70%，**55°C 之后彻底失去区分度、全程 99%**。手机核心温度到 55°C 并不困难，实际体感很可能是「大部分时间在满速」。用户想更安静，现在没有任何手段。
2. **曲线形状不是手感的全部。** 平滑步进是「每 2 秒最多动 5%」（`smoothStep = 5f` + `POLL_INTERVAL_MS = 2000`），即 0%→99% 要爬约 **40 秒**，降温回落同样 40 秒。用户画一条陡曲线，响应会明显滞后于预期。

### 上游参考

`mi-fan-control`（本 fork 的参考项目）**已有一套完整的曲线编辑器**，ColdFront 重写时整条丢弃：

- `SmartCurveEditActivity`：8 个固定节点，每点一对「温度/转速」输入框；步进模式（固定 / 3 段分段）；导出导入 JSON；恢复默认。
- `SmartCurveEditView`：Canvas 折线图，可拖节点（温度轴 30–100，转速轴 0–99）。
- `FanUtil`：`calcPwmByTemp` 插值、`getCurrentStep`、`saveSmartCurve`（存 `"30,0;35,30;…"` 进 SharedPreferences）。
- `FanRefreshService` + `FanUtil.handleScreenOff/handleScreenOn`：**息屏停转**（开关默认关闭、充电豁免、备份—恢复）—— 本功能同样已在上游实现，见 §8。

**上游的三个真 bug（本次必须修掉，不是风格问题）：**

| 上游问题 | 后果 |
|---|---|
| 拖点**不约束 X 单调** | 区间查找落空，ColdFront 移植版的落空分支**返回 0** → 曲线乱序则风扇**静默停转**，UI 还显示"智能温控运行中" |
| 只校验 `points.size() >= 2` | 乱序、重复 X、超范围的值都能落盘，错误被吞掉 |
| 曲线存 SharedPreferences 字符串，解析异常 `catch` 了事 | 与 ColdFront「解析失败必须报错，不当成空数据」的约定冲突 |

### 目标

让用户可编辑温度→转速曲线，**并且长期生效**；同时不破坏项目既有的两条底线：**写入诚实性**、**后台控制必须来自显式可撤销的授权**。

## 2. 已确认的设计决策

| # | 决策 | 选择 |
|---|---|---|
| 1 | 曲线形态 | **可拖点折线图 + 强制 X 单调** |
| 2 | 安全策略 | **只提示不强制** |
| 3 | 温度源 | **进本期** |
| 4 | Y 轴单调性 | **强制单调不减** |
| 5 | 生效范围 | **长期生效（复用常驻服务）** |
| 6 | 预设曲线 | **进本期**（静谧 / 均衡 / 性能） |
| 7 | 失效降级 | **回静谧档 + 交还系统控制** |
| 8 | 轮询频率 | **分屏状态节流**（亮屏 2s / 息屏放宽） |
| 9 | 息屏停转 | **新增**：开关式、默认关闭；**息屏交还系统控制** + 低频轮询双阈值（见 §8） |

## 3. 数据模型

### 结构

```
FanCurve
  points: List<CurvePoint>        // 默认 8 个，与上游/现有曲线一致
CurvePoint
  tempC: Int                      // 温度，°C
  pwmPercent: Int                 // 占空比，0–99
```

### 约束分两类（这是设计的核心分界）

混在一起会退化成"什么都没管住"，所以必须分开：

| 类别 | 内容 | 处理 |
|---|---|---|
| **结构性约束**（曲线是否良构） | X 严格递增且相邻间隔 ≥1°C；点数上下限；temp ∈ 轴范围；pwm ∈ 0–99；**pwm 单调不减** | **强制**。不合格的曲线不是"有风险"，而是**算不出来**（上游乱序 → 返回 0 → 静默停转正是此类） |
| **安全建议**（行为是否冒险） | 高温区转速偏低 | **只提示**（见 §5） |

> Y 单调归入结构性约束的理由：非单调曲线让同一温度对应两个转速，运行时表现为抖动；它不带来任何有意义的表达力（要迟滞应用专门的迟滞参数，而不是让曲线回勾）。

### 轴范围（建议值）

- 温度轴固定 **20–100°C**（容纳电池温度等低量程源），默认曲线覆盖 30–90。
- 转速轴 **0–99%**。

### 校验失败时的行为

- **保存**：拒绝保存，指出具体哪个节点违反哪条约束（不静默丢弃用户编辑）。
- **磁盘解析失败**：**报错并回退默认曲线，且明确告知用户**，不静默当成"没有曲线"。风格对齐 `data/ProfileJson.kt`（解析失败抛 `IOException`，而非返回空）。

### 持久化

- 沿用现有 DataStore（`cooler_settings`），曲线存为 **JSON 字符串**（单 key，如 `smart_curve_json`）。
- JSON 需带 **版本字段**，为将来模型演进留路。
- 序列化用项目已有的 `org.json`（与 `ProfileJson` 一致）；`kotlinx-serialization-json` 虽在依赖里，但不必为此新引风格。

### 迁移

**不需要迁移。** 可拖点模型的默认值就是现有硬编码的 8 个点原样，老用户行为零变化。（若当初选「固定温度栅格」才需要采样迁移。）

## 4. 编辑态 vs 生效态

**编辑曲线本身绝不写任何硬件节点。**

- 拖动 / 输入只改草稿状态；
- **保存**才写入持久化，并在 SMART 已开启时重新计算、写入一次目标占空比；
- 这与当前「用户不点启用就不接管」的设计一脉相承，也符合项目的写入诚实性约定。

## 5. 「只提示不强制」的落地

### 关键原则

**警告如果只在保存时弹一次，用户离开页面就忘了。** 三层，其中第三层最重要。

### 第 1 层 — 编辑时（图上）

- 把**参考基线**画成虚线。基线直接复用现有默认曲线，不凭空规定安全值：有据可依（来自参考实现的厂商默认值），用户一看就懂——"虚线是默认，我把它压低了"。
- 用户曲线低于基线的区段染警告色。
- 旁边实时显示当前点在读数值："58°C：你的 40% ／ 参考 90%"。

### 第 2 层 — 保存时（确认）

- 仅当命中**危险判定**时弹一次**说清后果**的确认（不是一闪而过的 Toast）。
- 用户确认后保存，并**记住这个决定**，不要每次打开都再拦一次。

### 危险判定不能等同于「低于基线」

**这是个容易踩的坑**：静谧预设（§7）本来就是刻意比默认线安静，如果拿"低于基线"当危险判定，**选一个自带预设就会满屏警告**。

所以判定要独立且宽松得多，只拦截「明显会出事」的配置：

- 建议规则：**温度 ≥60°C 时 pwm <50%**，或 **≥55°C 时 pwm <20%**（建议值，待标定）。
- **预设永不触发警告。**

### 第 3 层 — 运行时（首页）★ 最关键

当**实际温度**落在"低于基线"的区段时，在首页智能温控卡片挂一条**持续提示**，例如：

> 当前曲线在 58°C 时仅 40%（参考 ≥90%）

用户平时看的是首页，不是编辑页——只有这一层才真正起作用。

### 诚实说明后果

既然不强制，就必须如实告诉用户后果。**技术前提需实机验证一次再定稿文案**：

- SoC 有独立于风扇的内核级热降频保护，最坏结果更可能是**降频、卡顿、机身烫**，而不是物理烧毁；
- 但我们已经写了 `cooling_fan_enable 0`，系统那套风扇策略交出去了，**热降频很可能比系统接管时来得更早**。

> 验证方式：故意画一条高温区低转速的曲线，观察是否提前降频、机身温度与体感。

## 6. 温度源（本期）

现状：硬编码 `FanNodes.DEFAULT_TEMPERATURE_SOURCE = 0`（核心温度 `thermal_zone23`），不可选。`FanNodes` 里实际躺着 **8 个可用温度源**。

### 为什么必须一起做

曲线 X 轴的语义完全依赖它。核心温度波动剧烈、瞬时飙高，用它做基准，曲线会频繁被顶到高转速——**用户容易误判成"自定义曲线没用"**。

### 三个连锁反应

1. **首页大字温度会跟着变。** `pollOnce` 用选定源读快照，温度直接进 `state.temperatureC`（首页 TempHero 大字）。这是好事（一致），但是可见的行为变化。

2. **三个调用点必须统一到同一来源**，否则会出现"检查项显示的温度"和"曲线实际用的温度"不是一个东西——这违反项目的诚实性：
   - `FanManager.applySmart` → `readTemperatureC()`
   - `FanManager.pollOnce` → `readSnapshot()`
   - 运行检查 → `RootFanProbe(temperatureSource = …)`

3. **X 轴量程错配（需要处理）。** 各源量程差别很大——核心温度可能 30–90°C，**电池温度大概只有 25–45°C**。轴固定 20–100 时，选低量程源会导致**整条曲线只用得上左段**，风扇长期卡在低速端。

   处理方式（不引入模型复杂度，只把信息摊开）：
   - 图上标出该源的**典型工作区间**（各源实测量程需在实机标定后填入）；
   - 运行时游标顶到图右端时提示"已超出曲线范围"。
   - 游标一旦贴到边缘，用户自己就看懂了，无需文字解释。

> 未采用的方案：按源分别保存曲线（切换源等于换尺子，复杂度陡增）。

## 7. 预设曲线（本期）

| 预设 | 说明 |
|---|---|
| **静谧** | 刻意压低，高温区才拉起 |
| **均衡** | **= 默认 = 现有硬编码曲线原样**（老用户行为不变） |
| **性能** | 更早拉起、更早满速 |
| 自定义 | 用户拖动后的状态；与预设并列展示 |

预设解决了"90% 用户不会画线"和"默认值该是什么"两个问题。**预设永不触发危险警告**（见 §5）。

建议起始值（**待实机标定**；均满足单调不减）：
- 静谧：`40→0, 45→20, 50→40, 55→60, 60→75, 65→90, 70→99, 90→99`
- 性能：`30→40, 35→60, 40→80, 45→90, 50→95, 55→99, 60→99, 90→99`

## 8. 长期生效与失效安全

### 好消息：后台执行链早就存在

| 已有组件 | 现状 |
|---|---|
| `service/CoolerService` | 前台服务，`foregroundServiceType="connectedDevice"`，`START_STICKY`（被杀会重启） |
| `service/BootReceiver` | 已声明 `BOOT_COMPLETED`，**开机已有恢复逻辑** |
| opt-in 契约 | `profiles.setServiceProfile(id)` 把"允许后台自动控制"**持久化**；关停前先写退出标记 |
| 通知栏 | 已显示模式（`serviceNotification` 的 `serviceAutoOn`） |

关键：**曲线由 `curvePwmForTemp` 消费，而它就在 `FanManager` 里**——正是这条后台链驱动的东西。曲线一旦替换硬编码常量，**会自动被现有后台执行 + 开机恢复链消费，无需另建一套。**

### 不推翻既有契约，而是复用它

项目的规则不是"禁止后台控制"，而是：**后台自主控制必须来自一次显式、持久化、可撤销的授权**。

> `BootReceiver` 原话：*"An active device alone is not consent to start background auto mode."*
> `CoolerService` 原话：*"boot/sticky restart cannot silently re-enable the device."*

所以正确做法是**把"曲线激活"也做成一条同样性质的持久化意图**，复用它，而不是发明一个新的隐式自启。README 里"启动时只读挂载、不立即接管"不需要推翻——它说的是 App **冷启动**不自动接管；服务由持久化授权驱动是另一回事。

### 增量工作

主要是：**让 `FanManager` 从持久化读曲线**（现在是构造时写死的），以及曲线变更时生效 + 通知刷新。

### 失效安全（必须实现）

曲线不制造新风险，而是**放大既有风险**——因为用户会开始依赖它。

| 失效场景 | 现状行为 | 长期生效后的问题 |
|---|---|---|
| 进程/服务被杀 | `cooling_fan_enable 0` 持久化，系统不管；风扇停在最后写入的占空比 | **停 99% 就一直吵，停 0% 就一直热，用户不知道原因** |
| 温度读不到 | 停手、保持当前转速 + 首页横幅提示（**当前场景是对的，因为用户在看界面**） | 用户不在看界面 → 风扇永远冻结，无人被告知 |
| root 失效 | 写入失败 + 熔断 | 同上，静默冻结 |

**已确认的降级策略：回静谧档 + 交还系统控制。**

- 写 `target_level 1`（静谧档）+ `cooling_fan_enable 1`（交还系统）。
- 既不让风扇停在极端值，**也不假装曲线还在生效**。

触发条件（建议）：
- 服务 `onDestroy` / 进程即将终止（能捕捉到的路径）；
- 温度连续 N 次读取失败（N 建议 3–5，即 6–10 秒无有效读数）；
- `su` 熔断触发。

> 注意：进程被 `SIGKILL` 或"强行停止"时无法执行降级写。这是**能力边界**，必须如实体现——见下条。

### 状态可见性

通知栏需扩展为显示曲线状态（如「智能温控运行中 · 自定义曲线」），并在一句文案里明确 **"在系统允许的范围内持续生效"**，不承诺"永远生效"。这是诚实性的一部分：不能让用户以为在跑，其实进程早死了。

### 息屏停转（新增）

**目标**：屏幕熄灭后停止风扇，省电、消除夜间噪音。

#### 上游已有实现，可直接借鉴

`FanRefreshService` + `FanUtil`（参考项目）：

- 开关 `screen_off_stop_fan`，**默认关闭**，位于高级设置；
- **充电时豁免**：`if (sIsCharging) 跳过息屏停转`。充电是最大的发热场景，这个判断必须保留；
- 熄屏前若 `rpm == 0`（风扇本就关着）则**不备份**，亮屏也无需恢复；
- 否则按当前模式备份（系统模式 / `target_level` / `targetPwmDuty`），写入停转；亮屏时按备份恢复，备份无效则降级到静谧档；
- 用 `mWasStoppedByScreenOff` 做幂等，避免重复执行。

#### 必须修掉的两个上游缺陷

**① 停转后必须挂起曲线执行。**

否则下一个轮询周期会把曲线算出的转速**写回去**，停转只能生效 2 秒。上游靠在刷新循环里检查 `mWasStoppedByScreenOff` 跳过控制逻辑（两处：行 264、313）。

ColdFront 的对应位置是 `FanManager.pollOnce` 的 SMART 分支与 `applySmart` —— **必须显式挂起**。这是本功能最容易漏、且症状最迷惑的一处（"息屏停转看起来生效了，两秒后又转起来"）。

**② 停转意图必须持久化，不能只放内存。**

上游的备份值与 `mWasStoppedByScreenOff` 都是静态字段/内存态。于是：进程在息屏停转期间被杀 → 重启后标记是 `false` → `handleScreenOn` 直接 return **不恢复**，而风扇停在 0%、`cooling_fan_enable` 仍是 `0`（系统不管）→ **风扇永久停转且无人兜底**。

这比"停在 99%"更危险：**停转 + 系统控制已关闭**是热安全上最差的组合。

→ ColdFront 必须持久化「停转中 + 备份值」，并在**服务启动 / 开机**时自愈：若标记存在且屏幕已亮，**立即恢复曲线**。

#### 控制权：息屏交还系统（已确认）

**息屏 → 交还系统控制**；亮屏 → 重新接管并恢复曲线。

节点语义（已在上游确认）：

| 动作 | 写法 |
|---|---|
| 交还系统 | `settings put system cooling_fan_enable 1` |
| 本应用接管 | `settings put system cooling_fan_enable 0` |
| 交给系统但指定档位 | `settings put system fan_mode <mode>`：`-1` 智能 / `1` 静谧 / `0` 高速 / `4` 狂暴 |

推荐息屏时写 `cooling_fan_enable 1` + `fan_mode 1`（系统静谧档）——让系统用最安静的策略接管。

**重要收益**：息屏期间由系统自己管风扇，**自带热保护**，因此进程被杀不再等于"风扇永久停转"。此前设计中最危险的残余风险由此基本消除。

**但它与"低频轮询兜底"有张力，需合并成一个语义**（本设计的解读，**待你确认**）：

| 状态 | 动作 |
|---|---|
| 息屏 | 交还系统（`cooling_fan_enable 1` + `fan_mode 1`）—— 系统在凉时自然停转 |
| 息屏 + 温度 < 下限（建议 42°C） | **收回控制权并停转**（`cooling_fan_enable 0` + `pwm_duty 0`）→ 真正的静音与省电 |
| 息屏 + 温度 ≥ 上限（建议 48°C，迟滞 6°C） | **再次交还系统** → 由系统热保护兜底 |
| 亮屏 | 收回控制权，恢复曲线 |

即：**凉时我们停转，热时交给系统**——"停转"与"高温兜底"两个目标同时成立。

**残余风险（缩小但未归零）**：若进程恰好死在"收回并停转"那一档，则风扇停转且系统未接管，直到服务重启或开机自愈。→ 因此「停转中」标记**必须持久化**，并在服务启动与开机时自愈（呼应坑 ②）。

#### 与失效降级的关系（不能混淆）

| | 性质 | 处理 |
|---|---|---|
| 息屏停转 | **用户主动意图** | 交还系统（见上），阈值内主动停转 |
| 失效降级（§8） | **故障兜底** | 回静谧档 + 交还系统 |

两者最终都落到"交还系统"，但触发原因不同：一个是用户意图，一个是故障。**通知栏文案必须区分**，不能让用户把故障当成正常息屏行为。

### 节流（与息屏停转耦合）

动机：`POLL_INTERVAL_MS = 2000` 且**每轮起一个 `su` 进程**。常驻 24 小时 ≈ **43,200 次 su 唤起/天**——不只是电，还有 root 框架（KernelSU/Magisk）的持续开销。

息屏停转改变了息屏期间的算法：**停转期间曲线不执行**（坑 ①），温度轮询的用途变为驱动上面的双阈值状态机。

| 屏幕 | 轮询间隔 |
|---|---|
| 亮屏 | 2s（不变） |
| 息屏 | **10–30s**（低频；用于双阈值判定与高温兜底） |

- 实现参考：`FanManager` 已有 `foregroundStarted` 这一生命周期信号入口（当前仅用于链路丢失判定），可复用同类模式注入屏幕状态；或用 `PowerManager.isInteractive` / `ACTION_SCREEN_ON|OFF`（上游即在服务里 `registerReceiver`）。
- 屏幕状态必须**由服务持有并告知 `FanManager`**，不要让它自己注册广播——生命周期归属要清晰。

## 附：必须守住的三条底线

1. **编辑曲线绝不写硬件节点。** 只在 SMART 模式下由现有轮询路径消费。
2. **后台控制必须来自显式、持久化、可撤销的授权。** 复用现有 opt-in 契约，不发明隐式自启。
3. **失效绝不静默。** 曲线不再生效时必须降级并告知，不能让用户以为风扇还在被保护。
